# 에이전트 루프 자동화 구현 계획 — 이슈에서 머지까지 손을 떼고 돈다

> **에이전트 워커에게:** task 단위로 구현한다. 단계는 체크박스(`- [ ]`)로 추적한다.

**목표:** 리드가 이슈를 세우고 손을 떼면 워커 기동 → PR → 리뷰 → (수정 요청 → 재작업) → 머지까지
사람 없이 돈다. 사람이 끼는 자리는 **고위험 승인과 최종 머지 버튼**뿐이다.

**설계 정본:** [`2026-08-08-ci-review-architecture-design.md`](2026-08-08-ci-review-architecture-design.md) §5
**선행 계획:** [`2026-08-08-ci-review-architecture-plan.md`](2026-08-08-ci-review-architecture-plan.md)

> **선행 조건**: CI 계획의 Task 7(기록기)이 끝나 있어야 한다. 재작업 기동이 리뷰 상태를 신호로
> 쓰는데, 그 상태를 만드는 것이 기록기다.

## 이 계획도 코드를 미리 쓰지 않는다

초안은 각 task 에 완성형 코드를 넣었다가 PR #24 3라운드 리뷰에서 **차단급 2건**을 맞았고,
**둘 다 그 미리 쓴 코드 안에 있었다**.

| 지적 | 무엇 |
| --- | --- |
| 신호 오류 | `reviewDecision` 은 **승인을 요구하는 규칙이 없으면 계산되지 않는다.** 이 설계는 승인을 요구하지 않으므로 그 필드는 영원히 비어 있다 — 재작업 루프가 **「할 일 없음」으로 조용히 초록**이 된다 |
| 자기모순 | 정체 감지 워크플로가 `set -uo pipefail` 아래 종료코드 1을 내는 스크립트를 파이프로 받아 **잡이 상시 빨강**이 된다. 바로 아래 줄에 「fail-open 이 의도적이다」라고 적혀 있다 |

CI 계획이 같은 이유로 코드를 걷어냈다. **이 계획도 같다** — task 마다 **읽어야 할 자리 · 지켜야
할 불변식 · 검증 방법**만 준다. **현행 코드와 GitHub 의 실제 동작이 정본이다.**

## 전역 제약

- **automation 은 `risk: low` 로 선언된 이슈·PR 만 집는다.** 하드 게이트(`gate declare`/`gate approve`)는
  지휘자의 도구 호출을 가로채는 훅이라 **Orca automation 은 그 훅을 지나가지 않는다.** 고위험을
  automation 이 집으면 게이트가 무력해진다. 고위험은 사람·지휘자가 직접 디스패치한다.
- **fork PR 은 어떤 automation 도 집지 않는다.** 공개 레포다 — 남의 PR 로 리드 노트북에서
  에이전트를 띄우면 원격 코드 실행이 된다. 모든 precheck 에 저장소 대조를 넣는다.
- **한 PR·이슈에 워커 하나.** 잠금은 라벨로 하고 **writer 는 automation 하나**다.
- **워크트리 나이로 생사를 판정하지 않는다.** Orca 의 `lastActivityAt` 은 생성 시각에 박히고
  터미널 활동으로 갱신되지 않는다 (2026-08-07 실측 — 일하는 리뷰어 5대가 이 때문에 회수됐다).
- **검사 0건은 통과가 아니다.** precheck·정체 감지는 검사한 대상 수를 세어 출력한다.
- 검증 스크립트는 **stdlib 전용**. 새 `scripts/verify_*.py`·`test_*.py` 는 워크플로에 배선해야
  `verify_ci_check_coverage.py` 가 통과한다.
- **AI 자기 언급 금지** · **main 직접 커밋 금지** · `git stash`·force push 금지 ·
  포트 3000·3010·8000·5432 불가침 · 개발 DB `fintech` 는 읽기만.

## 전역 불변식

| 불변식 | 근거 | 깨지면 |
| --- | --- | --- |
| **리뷰 상태를 `reviewDecision` 으로 읽지 않는다** | ruleset 의 `required_approving_review_count` = **0**. 승인을 요구하는 규칙이 없으면 GitHub 이 그 필드를 계산하지 않는다 | 재작업 루프가 영원히 「할 일 없음」이 되고 그 사실이 초록으로 덮인다 |
| **리뷰 상태는 reviews API 의 최신 리뷰 + `commit_id` 대조로 읽는다** | 리뷰마다 `commit_id` 가 있다 | 낡은 리뷰로 재작업하거나 재작업을 놓친다 |
| **정체 감지는 fail-open** — 잡을 빨갛게 만들지 않는다 | 정체는 사람이 볼 신호이지 머지를 막을 사유가 아니다. 상시 상태라 빨강이 상시가 된다 | 스케줄 워크플로가 상시 빨강이 되어 아무도 안 본다 |
| **리뷰어는 고치지 않는다.** 판정과 근거만 낸다 | `.github/review-prompt.md` | 심판이 선수가 된다 |
| **한 판정에는 한 모델만** | 폴백 체인이 이것을 깼다 | 한 판정에 저자가 둘이 된다 |

## Task 1: 큐 판정을 순수 함수로 만든다

automation 3종이 공유하는 질문은 하나다 — **「지금 무엇을 집어야 하나」**. 순수 함수로 만들고
테스트를 붙인다. precheck 스크립트는 이 함수를 부르기만 한다.

**읽어야 할 자리**

- `gh pr list --json` 이 실제로 주는 필드. **`reviewDecision` 을 쓰지 마라** (전역 불변식).
  리뷰 상태는 `gh api repos/{o}/{r}/pulls/{n}/reviews` 로 읽는다 — 어떤 필드가 오는지 직접 확인하라
- fork 판별 필드가 무엇인지 실제 출력으로 확인하라. `gh pr list --json` 과
  `gh api …/pulls` 가 서로 다른 이름을 쓴다

**만드는 것**: `scripts/agent_queue.py`(순수 판정) · `scripts/test_agent_queue.py` · 배선.

**불변식**

- 세 판정을 낸다 — 착수할 이슈 / 재작업할 PR / 회수할 워크트리
- **고위험은 집지 않는다** · **fork 는 집지 않는다** · **이미 워커가 붙은 것은 집지 않는다**
- **정리는 나이가 아니라 연결 PR 상태로 판정한다.** 연결 PR 을 못 찾으면 **보존**한다
  (모르면 안 지운다)
- 판정부는 **I/O 없는 순수 함수**여야 한다. GitHub 조회는 호출부가 한다

**검증**

- [ ] 위 네 경계를 각각 케이스로 못박는다
- [ ] **리뷰 상태 읽기를 실제 PR 로 확인한다** — 이 레포에 `CHANGES_REQUESTED` 리뷰가 달린 PR 을
      하나 만들고, 네가 고른 방법이 그것을 잡아내는지 본다. 동시에 `reviewDecision` 이 **비어
      있음**도 같이 보여 이 불변식의 근거를 PR 본문에 남긴다
- [ ] 검사 대상 0건이면 실패하는지 확인한다

## Task 2: 워커 기동 automation

**읽어야 할 자리**: `orca-ide automations create --help` — 특히 `--precheck` · `--base-branch` ·
`--workspace-mode` · `--disabled`.

**불변식**

- **`--precheck` 로 「집을 것이 있나」를 먼저 본다.** 없으면 워크트리가 아예 안 생겨야 한다
- 착수 표식은 **`agent: ready` 라벨**로 한다 (리드가 붙인다). `risk: low` 와 **둘 다** 있어야 집는다
- 워커는 **작업 시작 전에** 잠금 라벨을 걸고, PR 을 연 뒤 뗀다
- 오더에 §6.1 신원 설정과 커밋 전 확인을 싣는다

**검증**

- [ ] **`--precheck` 의 의미를 먼저 실측한다.** 항상 실패하는 precheck(`false`)로 `--disabled`
      automation 을 만들고 손으로 돌려 **에이전트가 안 뜨는지** 확인한다. `true` 로 바꿔 뜨는지도
      확인한다. **의미가 다르면 이 전략을 버리고 프롬프트 안에서 조기 종료로 바꾼다** —
      그 경우 매 틱 워크트리가 생겼다 지워지므로 트리거 간격을 늘린다
- [ ] precheck 스크립트를 손으로 돌려 종료코드를 확인한다 (집을 것 없음 = 1)
- [ ] **작고 안전한 이슈 하나로 끝까지 돌려 본다** — 워크트리 생성 → 오더 수행 → PR
- [ ] 확인 뒤 활성화한다. 처음에는 반드시 `--disabled` 로 만든다

## Task 3: 재작업 기동 automation — 루프를 닫는다

**이 계획에서 가장 중요한 task 다.** 지금은 리뷰가 「수정 필요」를 내는 순간 흐름이 멈춘다 —
워커는 알림을 안 받고 폴링도 안 한다. 실제 개발자는 알림을 받고 돌아오는데 우리 워커에겐
수신자가 없다.

**읽어야 할 자리**

- `gh api repos/{o}/{r}/pulls/{n}/reviews` 의 출력. 최신 리뷰 상태와 `commit_id` 를 어떻게
  뽑을지 직접 정하라
- **`reviewDecision` 은 쓰지 마라.** 이 레포의 ruleset 은 승인을 요구하지 않아 그 필드가
  계산되지 않는다 — `gh pr view <N> --json reviewDecision` 이 빈 값인 것을 직접 확인하고
  그 출력을 PR 본문에 근거로 남겨라

**불변식**

- 신호는 **「최신 리뷰가 `CHANGES_REQUESTED` 이고 그 `commit_id` 가 현재 head 와 같다」**이다.
  낡은 리뷰로 재작업하지 않는다
- **기존 브랜치를 이어받는다.** 새 브랜치를 파면 그 PR 에 push 할 자리가 없어진다
- 워커는 리뷰 본문과 **인라인 코멘트**를 모두 읽는다
- **반박도 산출물이다.** 지적이 틀렸다고 판단하면 고치지 말고 근거를 코멘트로 남긴다 —
  맹목적 반영은 리뷰를 의식 절차로 만든다
- push 하면 재리뷰가 필요해진다. 그 순환이 성립하는지가 이 task 의 완료 조건이다

**검증** — **이 task 는 실제 왕복으로만 완료된다**

- [ ] 작은 PR 을 열고 일부러 고칠 거리를 남긴다
- [ ] 리뷰어를 붙여 `Request changes` 판정을 받는다 (CI 계획 Task 7 의 기록기 경유)
- [ ] 네가 고른 신호가 그것을 **잡아내는지** 확인한다. 같은 시점에 `reviewDecision` 이 여전히
      비어 있음도 보여라 — 초안이 그 필드를 신호로 썼다가 무력해졌다
- [ ] automation 을 돌려 **워커가 그 PR 브랜치를 체크아웃해 고치고 push 하는지** 본다
- [ ] push 후 재리뷰가 필요해지는지 확인한다
- [ ] 명령과 출력을 PR 본문에 그대로 싣는다

## Task 4: 정리 automation — 나이가 아니라 PR 상태로 판정한다

2026-08-07 에 CI 의 시작 스윕이 **일하는 중인 리뷰어 다섯을 회수**했다. 원인은 Orca 의
`lastActivityAt` 이 생성 시각에 박히고 갱신되지 않는 것이다. **같은 실수를 반복하지 않는다.**

**읽어야 할 자리**: `orca-ide worktree list --json` 이 주는 필드. `lastActivityAt` 이 실제로
안 움직이는 것을 **직접 확인하라** — 워크트리에 무언가를 보낸 전후로 값을 재면 된다.

**불변식**

- **나이를 보지 않는다.** 연결 PR 이 머지·닫힘인 것만 회수한다
- **지우기 전에 각각을 확인한다** — 터미널 프롬프트에 사람이 입력해 둔 **미전송 텍스트**가
  있으면 건너뛰고 그 사실을 보고한다 (2026-08-08 에 리드 입력 두 개를 그렇게 발견했다)
- 미커밋·미push 가 있으면 건너뛴다
- **검사·회수·보존 건수를 항상 출력한다**

**검증**

- [ ] `lastActivityAt` 이 안 움직이는 것을 명령과 출력으로 보인다
- [ ] 지금 상태로 손으로 돌려 **살아 있는 워커의 워크트리가 회수 목록에 안 나오는지** 확인한다
- [ ] 미전송 텍스트가 있는 워크트리를 하나 만들어 **건너뛰는지** 확인한다

## Task 5: 정체 감지 — 멈춘 것이 보이게 한다

리뷰를 CI 밖으로 옮기면 **「아직 안 한 것」과 「죽어서 못 한 것」이 화면에서 같아진다.**

**Orca 가 아니라 GitHub Actions 가 맡는다** — Orca 가 죽었을 때도 「멈춰 있다」는 사실은 보여야
한다. 판단이 아니라 결정론적 조회라 CI 안에 있어도 설계의 경계를 어기지 않는다.

**불변식**

- **fail-open 이다.** 정체가 있어도 **잡을 실패시키지 않는다.** 정체는 상시 상태라(리뷰 대기 중인
  PR 은 늘 있다) 빨갛게 만들면 상시 빨강이 되고 아무도 안 본다.
  **초안이 여기서 자기모순을 냈다** — `set -uo pipefail` 아래 종료코드 1을 파이프로 받아
  스텝이 실패하는데, 바로 아래 줄에 「fail-open 이 의도적이다」라고 적었다.
  **스크립트의 종료코드가 잡 결과로 전파되지 않게 하고, 그것을 검증하라**
- 리뷰 유무 판정도 **`reviewDecision` 을 쓰지 않는다** (전역 불변식). 안 그러면 리뷰가 달린 PR 도
  전부 정체로 오인해 오탐이 된다
- **검사한 PR 수를 항상 출력한다** — 통과가 「정체 없음」인지 「아무것도 안 봤음」인지 구분되게
- draft PR 은 제외한다

**검증**

- [ ] **정체가 1건 이상 있는 상태에서 워크플로를 돌려 잡이 초록인지 확인한다.** 이것이
      fail-open 불변식의 유일한 증명이다. 정적 검토로 넘기지 마라
- [ ] 요약에 검사 건수와 정체 목록이 찍히는지 확인한다
- [ ] 리뷰가 달린 PR 이 정체로 오인되지 않는지 확인한다

## Task 6: 등록물을 문서로 남긴다

**automation 은 코드가 아니라 등록된 상태다.** 레포를 클론해도 따라오지 않는다.

**만드는 것**: `.docs/6-도구/에이전트-automation.md` · `CLAUDE.md` 에 포인터 한 줄.

**불변식**

- 등록 상태는 **실제 출력에서 뽑는다** (`orca-ide automations list --json`). 손으로 지어내지 않는다
- 담을 것: 등록 표(이름·트리거·precheck·오더 경로·하는 일) · **다른 기계에서 다시 세우는 절차** ·
  끄는 법 · 관측하는 법 · **알려진 한계**(게이트 우회 · Orca 의존 · cron 지연)

**검증**

- [ ] 문서의 명령을 그대로 쳐서 도는지 확인한다 (지어낸 플래그가 없는지)

축 ② 정체 감지(Task 5). 착수 표식은 Task 2 에서 `agent: ready` 라벨로 확정.

**미검증 전제** — 이 계획이 스스로 재는 것

1. **`--precheck` 의 의미** — Task 2 가 실측하고, 다르면 전략을 바꾼다
2. **리뷰 상태를 어떤 필드로 읽을 것인가** — Task 1·3 이 실제 PR 로 확정한다.
   `reviewDecision` 이 안 되는 것은 확인됐고, 대체 경로는 구현자가 정한다
3. **재작업 왕복이 실제로 도는가** — Task 3 이 실제 PR 로 확인한다

## 이 계획이 못 닫는 것

- **automation 은 하드 게이트를 우회한다.** `gate declare`/`gate approve` 는 지휘자의 도구 호출을
  가로채는 훅이라 Orca 가 내부에서 만드는 워크트리는 지나가지 않는다. 완화책(`risk: low` 만
  집는다)은 **automation 이 스스로 지키는 규칙이지 강제되는 것이 아니다.**
- **트리거가 cron 뿐이라 즉시 반응이 아니다.** 리뷰가 「수정 필요」를 낸 뒤 트리거 간격만큼 늦다.
- **고위험 작업은 여전히 사람·지휘자가 디스패치한다.** 의도된 경계다.
